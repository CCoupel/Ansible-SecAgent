Des agents
pour Ansible

Le problème

8 risques que vous prenez à chaque playbook

Ansible est un outil remarquable. Mais son modèle SSH classique crée des angles morts sécurité et des dettes opérationnelles que la plupart des équipes découvrent trop tard.

💥

Une machine compromise, toute votre infra exposée

Votre Control Node centralise les accès SSH à tous vos hôtes. Un token CI/CD leaké, une dépendance malveillante, un accès mal révoqué — et c'est l'ensemble de votre parc qui est à portée d'un attaquant. En une seule étape. Sans alarme.

La surface d'attaque croît linéairement avec la taille de votre infra.

🔑

Révoquer une clef SSH : une urgence à 3h du matin

Une clef volée. L'horloge tourne. Vous devez la supprimer sur 300 hôtes, maintenant. Avec SSH classique, c'est une opération manuelle, hôte par hôte, qui prend des heures — sans blacklist centrale, sans expiration automatique.

La rotation de clefs n'est pas un événement planifié. C'est une urgence.

📋

Qui a lancé quoi, sur quoi, et quand ?

Ansible n'a pas de log d'audit centralisé. Les traces restent sur le Control Node — modifiables, supprimables. En cas d'incident ou de contrôle ISO 27001, NIS2 ou SOC2, vous ne pouvez pas prouver qu'une configuration a été appliquée, ni par qui.

L'auditeur pose la question. Vous cherchez dans des logs dispersés sur plusieurs machines.

🚪

Tout le monde peut tout faire

Ansible n'a pas de RBAC natif. Sur un Control Node standard, quiconque a accès peut lancer n'importe quel playbook sur n'importe quel hôte. AWX apporte du contrôle d'accès — au prix d'une stack lourde, d'une base de données et d'une interface à maintenir.

Vos droits sont gérés dans Azure AD. Votre automation n'a aucun contrôle d'accès.

📡

Votre infra dérive. Vous ne le savez pas.

Ansible pousse une configuration, puis rien. Entre deux runs, un admin fait un changement manuel, un paquet se met à jour, une règle firewall est modifiée. Votre infra dérive silencieusement de l'état décrit dans vos playbooks — et vous ne le saurez qu'au prochain incident.

Push-and-forget n'est pas de la gestion de configuration. C'est de l'espoir.

⏸

Un hôte offline ? La tâche disparaît.

Un redémarrage inattendu, une coupure réseau — si un hôte est indisponible au moment du playbook, la tâche échoue et n'est jamais rejouée. En rolling deploy sur 50 machines, il suffit d'une qui redémarre pour avoir un parc partiellement patché, sans alerte.

Votre fenêtre de maintenance a 4 heures. 3 hôtes n'ont pas reçu le patch. Vous ne le savez pas.

🔀

Un hôte compromis peut attaquer votre Control Node

C'est votre Control Node qui initie les connexions SSH vers les hôtes. Un hôte compromis connaît son adresse IP — et cette machine détient les clefs SSH de tout votre parc. Compromettre un hôte → cibler le Control Node → accéder à l'intégralité de l'infrastructure.

Vous avez segmenté vos hôtes. Mais le Control Node est le dénominateur commun de tous vos segments.

🌐

Multi-cloud, multi-site : une dette réseau permanente

Production, DMZ, disaster recovery, cloud A, cloud B, sites edge — chaque segment doit avoir une route vers le Control Node. VPN site-à-site, peering cloud, tunnels SSH : chaque connexion est une règle firewall de plus, une surface d'attaque de plus, une configuration à maintenir.

Votre infra est multi-cloud. Votre automation ne devrait pas exiger un réseau plat entre tous vos environnements.

Ansible Control Node ──SSH──▶ Hôte cible ← BLOQUÉ derrière NAT/firewall
La solution

Le modèle inversé Ansible-SecAgent

Ansible-SecAgent inverse le flux de contrôle. L'agent sur l'hôte cible initie une connexion WebSocket persistante (WSS) vers le serveur relay. Ansible n'a besoin d'atteindre que le relay — jamais les hôtes directement.

Un serveur

Simple : un binaire Go

Un seul serveur relay suffit pour commencer. Pas de bus de messages, pas de base de données externe, pas de reverse proxy : l'état est un fichier et le TLS est natif.

  • secagent-server écrit en Go
  • Dispatch des tâches direct par WebSocket, une connexion par agent
  • TLS natif, rechargement des certificats à chaud
  • État dans un fichier authentifié (HMAC), secrets chiffrés (AES-256-GCM)
Actif / passif

Haute disponibilité par verrou

Le même déploiement Docker Compose tourne sur plusieurs hôtes, sur un stockage partagé. Une seule instance détient le verrou et sert ; les autres attendent sans ouvrir aucun port, puis reprennent si elle disparaît. Les agents se reconnectent seuls.

  • Un seul maître par répertoire d'état (relay.lock)
  • Instances secondaires : aucun port ouvert, aucun état chargé
  • Les agents connaissent plusieurs adresses de relay
  • Déploiement Docker Compose multi-hôtes

Limite connue : l'actif/passif sur un stockage partagé entre deux hôtes réels n'a pas encore été vérifié en conditions réelles (voir « Limites connues » plus bas).

Compatibilité

Votre Ansible existant, inchangé

Ansible-SecAgent s'intègre à Ansible par un plugin de connexion et par l'inventaire externe secagent-inventory. Vos playbooks et rôles restent écrits comme aujourd'hui : c'est le transport qui change. SSH reste disponible en parallèle.

Playbooks et rôles

La forme de vos playbooks et rôles ne change pas ; seule la connexion change (ansible_connection: relay). Limites actuelles : hôtes Linux uniquement, fichiers transférés inférieurs à 500 Ko.

SSH toujours disponible

Ansible-SecAgent ne supprime pas SSH. Les deux coexistent. Idéal pour une migration progressive : passez hôte par hôte sans rupture de service.

Inventaire dynamique

Le binaire Go secagent-inventory (inventaire externe Ansible) liste les agents avec leur statut et leur chaîne de relays ; les groupes portent le nom de vos relays. Vos inventaires statiques restent utilisables en parallèle.

become / sudo supporté

become est supporté ; le mot de passe est transmis via stdin et masqué dans les journaux.

Options du plugin (ansible.cfg, variables d'environnement, variables d'hôte) : voir la spécification des plugins.

Sécurité

Sécurité by design

Chaque décision d'architecture a une justification sécurité explicite, documentée dans le modèle de sécurité du projet. Ce modèle est évalué par des revues internes ; ce ne sont pas des audits externes ni une certification.

RSA-4096 par agent

Chaque agent génère sa paire de clefs RSA-4096 au premier démarrage. La clef privée ne quitte jamais l'hôte.

Enrôlement contrôlé

Tout enrôlement exige un jeton d'enrôlement créé par un administrateur, plus un challenge RSA-OAEP prouvant la possession de la clef privée. Sans jeton, le serveur répond 403.

JWT chiffré RSAES-OAEP

Le JWT retourné à l'agent est chiffré avec sa clef publique RSA. Illisible sans la clef privée, même en cas d'interception réseau.

Blacklist JTI

Révocation immédiate par JTI. La connexion WebSocket active est fermée avec le code 4001 et l'agent ne se reconnecte pas.

Dual-key JWT

Rotation des secrets JWT sans interruption de service, avec une période de grâce pendant laquelle les anciens jetons restent valides.

TLS obligatoire

WSS pour les agents et les liens entre relays, HTTPS pour l'API, TLS natif dans le serveur. L'API d'administration n'accepte le HTTP qu'en boucle locale ; ailleurs, TLS est exigé.

become_pass masqué

Le mot de passe sudo/su est transmis via stdin et masqué dans les journaux de l'agent, du serveur et du plugin Ansible.

AES-256-GCM

L'état du serveur est authentifié par HMAC et ses secrets sont chiffrés en AES-256-GCM avec une clef maître (RSA_MASTER_KEY).

Liens entre relays signés

Les relays s'authentifient par des jetons Ed25519 émis par la racine et vérifiés avec sa clef publique épinglée. Plus de secret de signature partagé entre voisins.

Rotation et révocation

Rotation de la clef de lien de la racine avec double acceptation, révocation d'un jeton propagée de proche en proche, rotation hors ligne de la clef maître (state rekey).

Relays chaînés

Plusieurs zones, un seul point d'entrée

Une racine agrège des relays enfants placés dans vos DMZ, clouds privés ou sites distants. Ansible ne parle qu'à la racine ; les agents ne parlent qu'au relay de leur zone.

Topologie en arbre

Un relay enfant n'a qu'un seul parent. Le lien s'ouvre soit de l'enfant vers le parent (pull), soit du parent vers l'enfant (push) selon vos règles de pare-feu.

Inventaire hiérarchique

Chaque relay devient un groupe Ansible portant son nom ; l'inventaire de la racine agrège toute la descendance. Les tâches sont routées vers le relay qui détient l'hôte.

Un agent local reste local

Un agent connecté localement est prioritaire sur la table de routage : un autre relay ne peut pas le détourner en déclarant le même nom d'hôte.

Jetons de lien signés par la racine

Rôles relay-child et relay-parent, jetons EdDSA émis uniquement sur la racine, clef publique racine épinglée sur chaque relay non racine. Sans ancre, le lien est refusé.

Rotation et révocation propagées

Rotation de la clef de lien avec double acceptation et confirmation par chaque relay ; la révocation d'un jeton coupe le lien concerné à tous les niveaux.

Limites d'admission

Quotas de tâches par agent et par relay, budget mémoire pour la sortie des tâches, quota de snapshots de topologie par identité de relay. Un relay saturé répond 429/503 explicites plutôt que de s'effondrer.

Event Hooks

Event Hooks — Actions configurables par JSON

Déclenchez des actions (notification, script, appel API, écriture de fichier) sur les événements de votre parc, sans écrire de code : un fichier JSON suffit.

4 types d'actions

shell, file, api et webhook (POST signé HMAC-SHA256).

Événements d'hôte

host.up, host.down, host.new, host.conflict, host.suspended, host.resumed et relay.updated, propagés le long de la chaîne de relays.

Contexte de chaîne

Variables {{relay_chain}} et {{relay_origin}}, filtre relay_chain_contains validé au chargement : une configuration mal formée est rejetée en bloc.

Journal sans secrets

Journal JSON Lines en ajout seul, secrets (HMAC, jetons, en-têtes) masqués. Rechargement de la configuration à chaud par SIGHUP.

Fonctionnalités

Implémentées par version

Chaque version est livrée par jalons, avec ses notes de version et son journal des changements sur GitHub.

v3.0.4 — Liens de confiance signés et exploitation
  • Jetons de lien relay ↔ relay signés Ed25519 par la racine, clef publique racine épinglée sur chaque relay non racine
  • Rotation de la clef de lien (keys rotate-link, double acceptation) et révocation propagée de proche en proche
  • state rekey : rotation hors ligne de RSA_MASTER_KEY avec sauvegarde et vérification ; state link-trust reset pour ré-épingler une ancre
  • Limites d'admission : tâches par agent et par relay, budget mémoire de sortie, quota de snapshots par identité de relay
  • Secrets par fichier (*_FILE) pour le serveur et le minion
  • Politique de connexion sortante des liens (anti-rebinding DNS, redirections jamais suivies)
  • --version sur secagent-server et secagent-minion ; les arguments inconnus sont refusés au lieu de démarrer
  • Suspension d'un agent visible dans l'inventaire des relays ancêtres
  • Correctif : la réponse d'une tâche synchrone durant plus de 15 s n'est plus coupée
v3.0.3 — Actif/passif, état fichier, TLS natif
  • Actif/passif dans secagent-server : verrou d'exclusivité, instances secondaires sans port ouvert
  • État dans un fichier authentifié (HMAC, anti-rejeu, secrets chiffrés) à la place de SQLite
  • TLS natif avec rechargement à chaud des certificats
  • Journal des actions de hooks en ajout seul, sans secrets
  • Correctifs de sécurité : renouvellement de jeton et enrôlement sans jeton, connexions WebSocket non authentifiées (versions antérieures concernées)
v3.0.2 — Événements et inventaire hiérarchique
  • Propagation d'événements host.* le long de la chaîne de relays, avec variables relay_chain / relay_origin
  • Inventaire hiérarchique : groupes Ansible nommés d'après les relays, ?relay= pour limiter à une descendance
  • Variables de groupe (RELAY_GROUP_VARS) transmises le long de la chaîne
v3.0.1 — Chaîne de relays
  • Topologie en arbre, liens pull (enfant → parent) et push (parent → enfant), handshake relay_hello / relay_ack
  • Routage hiérarchique vers le relay qui détient l'hôte ; l'agent local reste prioritaire
  • Révocation d'un jeton de relay avec fermeture du lien actif
v3.0.0 — Fondations
  • Spécification du mode repeater (topologie en arbre) ; retrait de l'ancien mode proxy (PROXY_MODE)
  • Pas d'implémentation du repeater dans cette version : elle arrive en v3.0.1
v1.x – v2.x — Socle
  • Agent secagent-minion : enrôlement RSA-4096, connexion WSS persistante, exécution par sous-processus, transferts de fichiers, become
  • Plugin de connexion Ansible en Python ; inventaire par le binaire Go secagent-inventory (inventaire externe Ansible)
  • CLI d'administration intégrée au binaire serveur (v1.1.0)
  • Event Hooks configurables en JSON (v1.1.0)
  • Mode proxy multi-zone (v2.0.0), remplacé par la chaîne de relays à partir de la v3
Management

Administrez depuis le terminal

La CLI cobra est intégrée au binaire secagent-server : aucun binaire supplémentaire. Elle s'utilise depuis le conteneur ou l'hôte du serveur.

🤖

Gestion des agents

Listez, suspendez, révoquez et autorisez les agents. Gérez leurs variables d'inventaire.

secagent-server minions list
secagent-server minions suspend <host>
secagent-server minions resume  <host>
secagent-server minions revoke  <host>
secagent-server minions vars set <host> key=value
🎫

Jetons

Créez les jetons d'enrôlement et les jetons de lien, listez-les, révoquez-les.

secagent-server tokens create --role enrollment …
secagent-server tokens create --role relay-child …
secagent-server tokens list
secagent-server tokens revoke <id>
🔐

Clefs et rotations

Rotation des secrets JWT, clef de lien de la racine, clef maître de l'état.

secagent-server security keys rotate
secagent-server keys link-pubkey
secagent-server keys rotate-link
secagent-server keys link-status
secagent-server keys retire-link-previous
secagent-server state rekey
📋

Inventaire et statut

Visualisez les agents et l'état du serveur, et consultez le journal des hooks.

secagent-server inventory list
secagent-server server status
secagent-server server stats
secagent-server hooks status
secagent-server hooks log

Détail des commandes et options : MANAGEMENT_CLI_SPECS.md

Roadmap

Prochainement

Le jalon « v3.0.5 — Durcissement et dettes issues de v3.0.4 » regroupe les thèmes suivants. Il s'agit de travaux planifiés, sans date annoncée.

Durcissement des secrets et de la clef maître

Longueur minimale partout et dérivation de la clef de chiffrement de l'état par une fonction dédiée.

Moins de fragilité à l'expiration des jetons d'agent

Éviter l'arrêt en masse des agents lorsque le JWT d'agent (1 h) expire.

Chaîne de livraison et exploitation

Attestation des images publiées, messages de démarrage plus explicites sur une ancre périmée, --version pour secagent-inventory.

Dettes de test, de CI et de documentation

Regroupées dans le jalon « v3.0.5 — Durcissement et dettes issues de v3.0.4 ».

Limites connues

  • Un relay qui monte en v3.0.4 ne peut pas revenir en v3.0.3 : l'état est migré et les liens relay ↔ relay sont coupés pendant la montée (prévoir une fenêtre annoncée).
  • Le JWT d'un agent dure 1 h sans renouvellement : après expiration, toute reconnexion repose sur le jeton d'enrôlement ; un jeton à usage unique ou expiré arrête l'agent (code 78). Utilisez un jeton réutilisable restreint par motif de nom d'hôte.
  • L'actif/passif sur un stockage partagé entre deux hôtes réels n'a pas été vérifié.
  • Périmètre actuel : hôtes Linux uniquement.
  • Les fichiers transférés doivent rester inférieurs à 500 Ko.
  • Sans changement du budget mémoire par défaut, un relay accepte au plus 204 tâches simultanées.
Architecture

Architecture

Go côté serveur et agent, WebSocket direct (WSS) entre agents et relays, état en fichier, plugin de connexion Ansible en Python, inventaire par un binaire Go. Détail dans le High-Level Design et les spécifications techniques.

Démarrer

Démarrer

Trois guides d'installation complets, maintenus avec le code. Commencez par le serveur, puis les relays enfants si vous en avez besoin, puis les agents.

Agent (hôtes gérés)

Le secagent-minion s'installe en service systemd sur chaque hôte. Il s'enrôle avec un jeton créé sur le serveur, puis garde sa connexion WSS ouverte. Aucun port entrant à ouvrir.

Guide d'installation de l'agent

Serveur (relay racine)

Le secagent-server se déploie avec Docker Compose, sur un ou plusieurs hôtes en actif/passif sur un stockage partagé. Les secrets sont fournis par fichiers ; l'état est initialisé une fois.

Guide d'installation du serveur

Relays enfants

Un relay enfant s'ancre sur la clef publique de la racine et reçoit un jeton de lien signé par elle. Il s'installe dans la zone qu'il dessert (DMZ, cloud privé, site distant) et agrège les agents de cette zone.
