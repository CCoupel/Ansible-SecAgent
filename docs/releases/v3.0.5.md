# Ansible-SecAgent v3.0.5 — Notes de version

> **Statut** : v3.0.5 est livrée par la branche `milestone/v3.0.5` (date du CHANGELOG : 2026-11-05). Le tag `v3.0.5` sera posé après le merge sur `main`.
> Version précédente publiée : **v3.0.4** (release GitHub du 2026-10-08).

## Résumé

La v3.0.5 ferme les dettes et les points de sécurité laissés par la v3.0.4 : les JWT d'agent sont renouvelés sans coupure, la clé maître est contrôlée, les actions CI sont épinglées et les images sont attestées. Elle change aussi la **licence du projet : AGPL-3.0-or-later**.

Il n'y a **pas de rupture de lien ni d'agent** depuis la v3.0.4. Lire la procédure de montée avant de déployer : `DOC/project/DEPLOYMENT.md`, « Montée de version v3.0.4 → v3.0.5 ».

## Changements notables pour les utilisateurs

### Licence AGPL-3.0-or-later à la place de MIT (#237)
- Le dépôt est distribué sous **GNU AGPL v3.0 ou ultérieure** (texte intégral dans `LICENSE`). Une licence MIT n'a jamais été publiée dans une version : elle n'existait que sur la branche de travail.
- Si vous proposez le programme modifié à des utilisateurs à travers un réseau, l'AGPL (§13) vous oblige à leur offrir le code source correspondant. Code source : <https://github.com/CCoupel/Ansible-SecAgent>.
- Les contributions passent par un accord de contribution (Harmony CLA 1.0, `CLA.md` / `CLA-entity.md`) : voir `CONTRIBUTING.md`. Chaque fichier source porte un en-tête SPDX, vérifié en CI.
- `LICENSE` et `THIRD_PARTY_NOTICES.md` sont joints aux binaires de la release, à l'archive Compose et aux images ; les images portent l'étiquette `org.opencontainers.image.licenses=AGPL-3.0-or-later`.

### `--version` sur 3 lignes
`secagent-server`, `secagent-minion` et `secagent-inventory` affichent :

```
<composant> version <version>
License: AGPL-3.0-or-later
Source: https://github.com/CCoupel/Ansible-SecAgent
```

La première ligne est inchangée. Un script qui lit la sortie entière doit être adapté (ceux du dépôt lisent la première ligne). `--version` suivi d'un argument sort en 1 sur les trois binaires.

### Secrets du serveur via `*_FILE` : recommandé
Donner `JWT_SECRET_KEY`, `ADMIN_TOKEN`, `RSA_MASTER_KEY` et `REPEATER_UPSTREAM_TOKEN` par fichier (`*_FILE`, fichier régulier, non lien symbolique) plutôt que dans l'environnement : les variables d'environnement apparaissent dans `docker inspect` et dans `/proc`. Les Compose de qualif et de prod du dépôt utilisent désormais les fichiers.

### `RSA_MASTER_KEY` : 32 octets minimum (#214)
Le serveur refuse de démarrer avec une clé de moins de 32 octets ou prévisible. Si votre clé est trop courte, exécutez `secagent-server state rekey` avec le binaire v3.0.4 **avant** la montée.

## Nouveautés

- **Renouvellement des JWT d'agent (#217)** : renouvelés sur la WebSocket ouverte, persistés de façon atomique ; plus d'arrêt en masse des minions à l'expiration. `AGENT_JWT_TTL` (24 h) et `AGENT_JWT_RENEW_INTERVAL` (TTL/3).
- **Minion** : un 401 à la poignée de main est réessayé avec le même JWT avant d'être effacé ; ping applicatif des connexions agent.
- **CLI** : `minions delete`, `relays revoke`, `relays remove --revoke`, `relays add --token-file` (#233) ; sous-commande inconnue d'un groupe : code 1 (#219).
- **Liens relay** : statuts `never_seen` / `not_direct` à la rotation des clés de lien, quota `event_forward` par `relay_id`, refus explicite d'une ancre périmée (#215, #216, #218, #234).
- **Préparation PROD (#248)** : `gorilla/websocket` 1.5.3 et `jwt/v5` 5.3.1 (`govulncheck`), binaires en Go 1.27.3, `govulncheck` en CI, fichier `VERSION` contrôlé face au tag, ports hôte PROD paramétrables (`API_PUBLISH_PORT`, `WS_PUBLISH_PORT`, `ADMIN_PUBLISH_PORT`).
- **Images et CI** : provenance SLSA des images (#213), actions épinglées par SHA avec garde, `actionlint` / `shellcheck`, Dependabot traité (#199 à #205).
- **Qualif** : MooseFS qualifié comme stockage partagé de l'état actif/passif (#239), refus 503 en réel (#241), minions durcis (#238).
- **Données privées du poste sous `PRIVATE/` (#250)** : secrets, PKI de test et jetons de la qualif sous `PRIVATE/qualif/` (jetons de chaîne volatils dans `${TMPDIR:-/tmp}/secagent-qualif-chain-<uid>` ; racine `SECAGENT_PRIVATE_DIR`) ; `PRIVATE/prod/` ne porte que du public (`ca.crt`, `.env`) et la référence des secrets PROD est `~/secagent-private/prod/` (ext4, hors dépôt), jamais sur l'hôte ni dans l'archive.

## Montée depuis v3.0.4

1. Vérifier la longueur de `RSA_MASTER_KEY` (≥ 32 octets) ; sinon `state rekey` en v3.0.4.
2. Sauvegarder `relay.state` de chaque relais et le vérifier (`state verify`).
3. Déployer les binaires v3.0.5.

**Retour arrière** vers v3.0.4 : arrêter tous les nœuds, `state restore --from <sauvegarde>`, binaires v3.0.4 avec la même clé maître.
